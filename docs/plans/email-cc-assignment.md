# 邮件抄送展示与自动分配规划

日期：2026-09-08。
状态：用户已确认本规划；后续复审发现的问题已修复，Luna（max effort）已完成独立复审与限定增量复核，主代理最终验证通过。尚未提交、部署或启用线上功能；真实邮件收发验收保留为发布前检查。

## 1. 目标与范围

客户将请求发送至系统接收邮箱，同时抄送技术支持。平台展示每封邮件的抄送信息，并在创建新邮件工单时优先分配给能够明确识别的抄送技术支持。

- 使用现有 Zammad 6.5.2 邮件接入、工单和用户 API；升级 Zammad 单独安排。
- 管理员和技术支持可查看 CC；管理员继续使用现有手动分配入口。
- 自动分配只作用于新邮件工单的初始负责人。历史工单不批量重分配，后续回复只更新消息展示。
- 客户长期服务分组、区域归属和权限体系继续作为基础约束。
- 不扩展为根据正文识别人员、邮箱别名推断、多人共同负责或自动回复全部抄送人。

## 2. 已明确的基础

- 当前实例的邮件文章 API 已实测返回非空 CC；字段为字符串或 null，常见格式为“姓名 <邮箱>”。平台消息 API 已透传。
- 原邮件路由根据客户服务分组确定区域和固定负责人；批量自动分配跳过待分配区，并只处理未分配工单。
- 管理员更改客户服务分组或分组负责人时，现有流程会迁移相关未关闭工单。这属于主动管理操作，应继续生效。
- 本轮之前的只读检查中，当前 Zammad 启用的触发器负责自动回复和 Webhook，未发现 owner/group 分配动作；调度任务为空。发布前如外部配置发生变化，应重新核对。

## 3. 已确认业务规则

用户已确认下列规则，以此作为开发及验收依据。

### 抄送展示

在每条邮件消息的发件人信息附近增加“抄送：姓名 <邮箱>”。保留完整地址，支持复制和多行换行，空值隐藏，按普通文本渲染。每条消息展示自身 CC，避免把后续邮件的抄送名单误认为首封来信的分配依据。补齐六种语言文案。

### 分配决策

以下 CC 优先规则在 `EMAIL_CC_AUTO_ASSIGN_ENABLED=true` 时生效；未开启时继续使用固定负责人。先确认工单位于待分配区、尚无实际负责人、状态为 new/open，且触发消息确为 Zammad 中的首封公开客户邮件；然后按下表决策。

| 条件 | 处理 |
| --- | --- |
| 客户有服务分组，CC 唯一匹配可承接坐席 | 使用客户原区域，分配给该抄送坐席，即使其不同于固定负责人 |
| 无 CC、无符合条件匹配或多人符合条件 | 回退客户服务分组固定负责人 |
| 固定负责人不可用，但 CC 有唯一合格匹配 | 分配给抄送坐席 |
| CC 和固定负责人均不可用 | 保留待处理，通知管理员 |
| 客户尚未配置服务分组 | 保留待处理，通知管理员，不根据 CC 推断区域 |
| 已分配工单、回复邮件、系统自动回复、网页消息 | 不触发 CC 初始分配 |

“可承接坐席”指：账号已启用，具备 Agent 角色，非管理员和系统邮箱，未休假，并对客户所属区域拥有 full 权限。仅按平台账号的完整邮箱匹配，忽略大小写并去重；不把显示名中出现的邮箱当成收件地址。多个 CC 中只有一个合格坐席时，可分配给该坐席。

已确认的产品选择：CC 优先于固定负责人；多人合格时回退固定负责人；无客户服务分组时不自动分配。这三点决定与原业务规则的关系。

## 4. 与现有流程的协调

CC 作为现有邮件路由内部的一次初始决策，不新增第二个并行分配任务。

- 从 Zammad 拉取首篇原始文章，避免 webhook 缺少 CC 或快速自动回复被误判。
- 决策前读取当前工单，写入前再次检查 owner、group、state、customer 和负责人变更标记，放弃已经变化的分配任务。
- 用一次 API 更新写入 group、owner 和 state，消除原来先移组、再设负责人的中间状态。
- 同进程重复回调串行处理；已成功分配的工单重放时跳过。
- 定时分配继续跳过已有负责人的工单；管理员明确取消区域工单分配后，再运行批量分配仍采用服务分组负责人。
- 管理员主动改派或迁移服务分组可以覆盖初始 CC 分配，后续邮件不会把它改回。
- 写入超时不直接回滚，避免远端已经成功却被撤销；记录异常并提示管理员核查。

并发限制：Zammad 6.5.2 REST 接口没有条件式 owner 更新。上述措施处理过期状态、重复事件和两步更新冲突，但无法承诺跨实例或外部管理操作在最后一次读取和写入之间的严格互斥。上线前需要确认部署实例数量；强互斥需求应单独评估统一写入入口或 Zammad 侧能力，不能仅靠进程内锁宣称解决。

## 6. 验收标准

- 管理员和技术支持能看到每封邮件的真实 CC，空值不占位，长地址不破坏布局。
- 唯一合格 CC 可优先于固定负责人；无匹配、多人、账号停用、休假、权限不足时符合决策表。
- 无服务分组或无人可承接时，工单留待处理且管理员获得通知。
- 重复回调、快速系统回复、后续客户回复不会重复通知或改变已经完成的初始分配。
- 管理员改派、服务分组迁移、定时分配以及普通网页建单继续符合原有规则。
- 独立 CC 开关关闭后，新邮件恢复服务分组分配，已分配工单保持现状，CC 展示仍然可用。
- 类型检查、相关回归测试和六种语言校验通过；在隔离环境完成一封真实抄送邮件的接收、展示、分配、通知和后续回复验证。

## 8. 后续复审修复

主代理随后新增隔离复现，发现原有 104 项测试未覆盖两种情况：原始邮件读取失败被确认成功，导致待分配工单没有重试机会；带组名的合法 CC 中第一项被丢弃，导致多人误判为唯一匹配。此前的“未发现阻断问题”仅代表当时覆盖范围，不作为最新审查结论。

修复策略：

- 技术读取或写入失败向 Webhook 返回可重试结果，HTTP 503 请求上游重试，并尽力通知管理员；业务上确实无法分配的情况仍由管理员处理。
- 重试依赖当前 Zammad 工单状态，已完成的写入不重复执行，也不因响应丢失而回滚。
- 采用保守 CC 解析：不支持的地址组或任意未能完整解析的非空项使整个列表回退固定负责人，避免从残缺列表推断唯一匹配。
- 增加依赖读取各阶段、空文章列表、告警失败、原始 webhook 重试恢复、更新成功但响应丢失和地址组回退的回归用例。

Luna 已按用户指定的 max effort 完成第一轮独立复审：未发现阻断级问题，但提出注释/空收件项解析策略与 503 前已写入 TicketUpdate/SSE 两项 P2。主代理已修复并增加回归：对空项及引号外注释整体回退；将邮件路由移到事件持久化、广播和普通事件通知之前，使失败尝试不生成重复事件。Luna 已完成限定增量复核，结论为通过、未发现本次增量引入的新缺陷。
